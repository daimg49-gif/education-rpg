# 校園真相調查局｜互動式教育 RPG 開發手冊

> 專案：`daimg49-gif/education-rpg`  
> 遊戲：<https://daimg49-gif.github.io/education-rpg/>  
> 紀錄日期：2026-10-10  
> 範圍：**只記錄本次「校園真相調查局」遊戲的腳本、操作、介面、美術與除錯經驗**；不納入期間其他教學活動、網站或系統開發。

## 0. 下次複製這套做法，先看這裡

這個專案的可複用模型是 **「探索地圖 → 蒐集資料 → 判斷立場 → 選擇標題與報導 → 引用證據 → 審查回饋 → 章節結案」**。它不是單純答題遊戲；學生先接觸具體、彼此可比對的資料，再自行推論。

新專案建議採以下順序：
1. 先寫五案／多案的**完整劇情與證據矩陣**，確認唯一合理結論，暫不寫程式。
2. 先製作**一個可完整通關的垂直切片**：開場、地圖、取證、編輯桌、通過與失敗回饋、結案。
3. 把案件內容資料化，讓共用引擎讀取案件設定，而非每案複製整套函式。
4. 建立固定地圖、角色、照片與文件樣式，再批次製作其他案件素材。
5. 每次修改**只動必要範圍**，測試正常、錯誤、缺資料、多選、重新開始及手機操作後才發布。

## 1. 教學定位與故事建構

### 學習目標
- 媒體識讀：來源查核、照片脈絡、截圖真偽、統計解讀、證據與推論分界。
- 將「媒體判斷」轉為故事內的實際任務：玩家是一名**校刊編輯員**，要查證傳聞，並在校刊社編輯桌發表有來源的正確報導。
- **不要讓資料自己告訴學生結論**：道具應呈現日期、紀錄、原始內容、署名、拍攝資訊、當事人原話，避免「這無法證明……」之類替學生下結論的旁白。
- 每案可有多個有用線索，但**標題與內文的標準答案明確唯一**；提示用追問，不直接洩漏答案。

### 五案劇情矩陣（現行故事）
| 案件 | 事件鉤子 | 重要事實 | 要學會的判斷 |
| --- | --- | --- | --- |
| 01 閱讀週的驚人數字 | 借閱量「翻倍」是否代表能力提升？ | 活動前一週 80 冊，閱讀週 164 冊；借閱紀錄、整理方式、集點辦法與學生訪談 | 借閱冊數≠讀完數量≠閱讀能力 |
| 02 消失的午餐 | 一張剩菜照片被說成學校供餐不足 | 10 月 8 日 12:32 用餐後照片；原圖被裁去空碗與骨頭；比對拍攝者、菜單與供餐紀錄 | 原圖、時間與裁切脈絡 |
| 03 不存在的校長公告 | 群組截圖宣稱下週全面禁止進入圖書館 | 正式公告 114-107 僅週三第二節下課暫停 20 分鐘 | 官方原始公告與轉傳截圖的不同 |
| 04 冠軍班級爭議 | 甲班總量最高、乙班人均較高，誰是冠軍？ | 甲班 120/30＝4 本/人；乙班 90/15＝6 本/人；原規則依總冊數排名 | 比較基準與既定規則 |
| 05 校園神祕黑影 | 模糊監視器黑影引發闖入傳聞 | 18:42 模糊畫面；18:35–18:50 設備搬運紀錄；對照值班與時間線 | 模糊影像不足以確認身分，證據應交叉核對 |

### 每案腳本模板
編寫新一案時先備齊：
- **傳聞原文**：真的有人會這樣轉傳的短句，讓學生有調查動機。
- **委託人與疑問**：例如阿甘詢問「這句話有何依據？」
- **具名角色**：學生、老師、轉傳者、當事人；使用可信、具體的原話。
- **證據資料卡**：ID、名稱、場景、座標、資料全文、來源、日期或數字。
- **教師私用證據評分表**：必要／可補充／不得作為該報導依據。*分類只存在內部資料，不向學生顯示。*
- **可發表的標題與內文**：每組三選一，另外兩個錯誤選項各自代表明確的認知誤區；避免「可能」「值得查核」等過度模糊、容易多解的選項。
- **刊登後的閱讀回信與下一案線索**：收尾要與學生實際引用的資料一致。

## 2. 整體流程與互動機制

### 開場
開場**必須在遊戲地圖操作前**顯示：第一頁說明玩家身分與四步通關方式，第二頁揭露第一案傳聞與主編委託，玩家按「接受委託」才進入地圖。

本專案曾有「只看到地圖、開場不見」的錯誤，最後採用**獨立且在遊戲引擎執行前即寫入 HTML 的全螢幕開場**，不依賴地圖對話視窗在初始化後才出現。

### 地圖與操作
- 16×9 格地圖，`canvas` 邏輯尺寸 **640×384**；tile 約 40px。
- 五個場景：**圖書館、四年級教室、校刊社、校園走廊、資料室**。位置與出口連接固定。
- 桌面：方向鍵／WASD；手機：畫面方向按鈕、調查／對話鍵；支援長按連續移動。
- 靠近 NPC／文件才可互動。場景內物件含 `id`、`label`、`text`、`x`、`y`。
- 玩家點取資料→加入已發現資料→在編輯桌引用；紀錄板可以貼上查到的資料，但**貼上紀錄板**與**校刊引用勾選**是不同操作。
- 玩家到**校刊社編輯桌**依序完成：立場→標題→內文→引用證據。不能跳過編輯而靠抵達地圖自動過關。

### 審查規則與保密
共用 `caseWizard()`、`editorConfig()`、`evaluatePublication()`、`publicationGuard()` 讓五案使用一致流程。內部 `evidenceRubrics` 定義 `necessary`、`supplementary`、`counter`，應當：
- 必要證據：全部引用才通過。
- 補充證據：可任意引用或不引用。
- 不適切引用：只要列入引用就要讓學生重新審查。
- 立場、標題、內文還要與資料支持的結論相符。
- **學生頁面不要印出分類、必要證據清單或標準答案。** 只顯示蒐集到的資料名稱與勾選狀態；失敗訊息用證據品質／可追溯性來引導。
- **不要加入未列入評分表的隱藏條件**：否則學生即使引用正確資料也會卡關。
- 「反證」本身不等於錯誤訊息。資料分類應依其**是否支持目前刊登的主張**來決定；製作其他主題時重新審閱分類。

### 完成與重置
- 每案成功刊登才可進入下一案。
- 第五案完成後顯示五案回顧與教學提問。
- 本專案目前設計為**重新整理即清空進度**：`save()` 不持久化，舊版 `localStorage` 紀錄於載入時清除。新專案如要續玩，必須獨立設計並測試存檔策略。
- 「重新開始」需同時清除案件進度、地圖位置、對話狀態、結局與開場頁次。

## 3. 遊戲畫面與視覺設計

### 主要畫面
1. **全螢幕開場卡**：深藍背景／金色框線，資訊分段成「角色身分、通關任務、事件引子」；重要詞可少量用紅色標示。
2. **俯視像素風探索地圖**：固定座標與房間關係，角色、可互動人物／道具、方向出口與迷你地圖；場景切換不旋轉座標。
3. **故事／資料視窗**：當前場景細緻插畫背景，深色半透明對話板，按鈕置於正文後。
4. **文件卡**：米黃紙面、深色字、外框，像實體資料夾／紀錄簿，資訊要具體可信。
5. **校刊編輯精靈**：四步選項、單選標題與內容、多選引用，已選項清楚顯示，未通過有可操作的下一步。
6. **結案回顧**：每案學習要點、問題與重玩入口。

### 美術製作規格
- 地圖由 Canvas 即時繪製：地板格、門、可互動家具、簡易像素人物與標記。
- 五個場景插畫檔位於 `assets/`：`library.webp`、`classroom.webp`、`newsroom.webp`、`hallway.webp`、`records.webp`。檔名與 `artFiles` 列表需一致。
- 角色與圖片要符合故事用途，不要以有美感但無關的裝飾取代查證資訊。
- **雙層風格**：地圖保持清楚的像素可操作感；對話／文件有較高細節，且不能犧牲文字可讀性。
- 文件紙面不套用黑色文字陰影。**2026-10-10 v3.5.5 已加入全站取消 `text-shadow` 的覆寫 CSS**，避免陰影從半透明對話框繼承到米色文件。
- 小螢幕需檢查長文滾動、關閉鍵是否壓住內容、選項觸控尺寸與可見性。

### 可重用的美術提示詞骨架
> 俯視角、教學用 RPG、清楚可讀的場景、16:9、溫暖的像素風，主要物件位於可互動網格內，門口與行走通道不被遮擋；無任務答案文字。

> 國小校園校刊社室內情境插畫，檔案櫃、文件、海報、柔和自然光；作為對話視窗背景，為深色文字面板預留空間；**不要在圖片內預先畫入遊戲 UI 或答案**。

圖片產出後還要測試實際裁切與手機顯示。對話框內的字請用 HTML 呈現，不要生成進圖片中。

## 4. 技術結構：複用時請逐步模組化

目前專案為單一入口 `index.html`（HTML + CSS + JavaScript），素材在 `assets/`。主要程式概念：
- `scenes`、`secondScenes`、`thirdScenes`、`laterCases`：場景與章節物件資料。現有資料結構歷經追加，**不完全一致**，新作不應照搬這個歷史負擔。
- `state`：位置、章節、蒐集、引用、已發表狀態。
- `draw()`、`move()`、`interact()`：地圖繪製、移動與互動。
- `openStory()`、`syncStory()`、`closeStory()`：視窗顯示與操作同步。
- `caseWizard()`：刊登流程；`editorConfig()`：統一案件設定；`evaluatePublication()`：純粹判定證據與報導；`publicationGuard()`：依結果回饋。
- `startSecond()`、`startThird()`、`startLater()`：各案切換；`showReflection()`：五案結束頁。
- `firstCaseIntro()` 搭配獨立開場初始化：先告訴玩家玩法，再揭露第一案。

**下次新專案的建議檔案分層**（非宣稱現有專案已拆分）：
```text
index.html
styles/
  game.css
src/
  cases.js          # 所有案件/場景/證據/選項設定
  state.js          # 初始狀態、重置、存檔
  engine.js         # 地圖、碰撞、移動、互動
  story-ui.js       # 對話、文件卡、開場
  editor.js         # 四步寫稿與審查
  main.js           # 啟動與事件綁定
assets/
  library.webp
  classroom.webp
  newsroom.webp
  hallway.webp
  records.webp
docs/
  GAME_DEVELOPMENT_PLAYBOOK.md
```

## 5. 這次踩過的坑與確切預防方式

| 發生過的問題 | 已發現原因／教訓 | 下次預防 |
| --- | --- | --- |
| 一開遊戲只看到地圖、沒有開場 | 開場原先依賴遊戲主程式中的一般對話 UI | 開場採引擎前獨立 HTML，測試首次載入與重玩 |
| 開場出現字面 `\n` | 過度跳脫字串，反斜線被直接顯示 | 使用真實 HTML 區塊及 DOM 元素，不把排版塞成長字串 |
| 按「發表校刊」像沒反應 | 視窗複製按鈕事件和審查限制曾交錯，失敗訊息不明確 | 同一入口處理所有案件；點擊必有成功或具體可操作回饋 |
| 正確證據仍卡關 | 曾有額外調查條件未在同一個評分表內 | 只使用明確的內部必要／可選／不適切清單判定 |
| 三類證據直接顯示給學生 | 將教師／程式用評分資訊直接渲染到 UI | 學生只看到證據名稱；評分分類僅留在邏輯層 |
| 點選後顯示「操作未完成」 | `letters.replaceChildren is not a function`：`letters` 曾是假的占位物件，缺少 DOM 方法 | `quest`、`history`、`letters` 使用真實存在的 DOM 元素；移除不完整占位物件 |
| 瀏覽器整頁顯示 JavaScript 原始碼 | 修改時意外把 JS 附加在 `</html>` 之後 | 寫入前驗證開頭 `<!doctype html>`、結尾 `</html>`、腳本標籤配對及所有腳本語法 |
| 米色文件上的字有嚴重陰影 | 深色故事對話框的 `text-shadow` 被文件內容繼承 | 文件文字顏色與文字陰影要獨立控管；測試含長文的文件卡 |

**特別注意**：JavaScript「語法通過」不代表 UI 功能正常。這次最重要的教訓是**每次修正要用實際通關路徑測試，而非僅靠解析程式成功**。

## 6. 發布前驗收清單

### 劇情
- [ ] 開場遊戲說明顯示；按下一步揭露第一案；再按開始才顯示地圖。
- [ ] 五案傳聞、當事人、文件與報導選項彼此一致。
- [ ] 選項唯一合理，錯誤選項各代表一種可辨識的推論錯誤。
- [ ] 學生畫面沒有「必要證據」「標準答案」或提前破案的提示。

### 操作
- [ ] iPhone 方向鍵單擊、長按；行走、場景轉換、角色互動。
- [ ] 每張資料卡可閱讀、關閉、加入紀錄板；不意外遮住按鈕。
- [ ] 校刊四步皆能前進、返回、重選與多選。
- [ ] 五案各測：只有必要證據、必要+補充、缺必要、包含不適切、未選證據。
- [ ] 每種失敗都能收到回饋並返回可操作頁面。
- [ ] 各案成功發表後可結案、開下一案，最後到五案總結。
- [ ] 重新整理、重新開始都回初始區／開場且不保留舊狀態。

### UI 與品質
- [ ] 手機視窗沒有內容被固定的「返回探索」遮擋。
- [ ] 文件長文好讀，字體無陰影，深淺對比足夠。
- [ ] 插圖找不到時有替代處理，對話按鈕仍可用。
- [ ] `index.html` 僅有合法 HTML 內容；腳本配對與語法檢查通過。
- [ ] 在**實際部署網址**測試，而非只測本機或檔案片段；避免 CDN／瀏覽器快取混淆版本。

## 7. 交給 AI 接續開發時可以直接貼的工作規格

> 請以 `daimg49-gif/education-rpg` 的模式為參考，製作一個給國小學生使用的互動式教育 RPG。採用五場景地圖、角色對話、可收集文件、四步編輯／判斷流程、關卡結案與總回顧。先提出完整故事和證據矩陣，驗證每案唯一答案，再開發可完整通關的第一案。互動與 UI 要優先適配 iPhone。評分依必要／補充／不適切證據設定，但不得向學生公開分類。所有按鈕必有反應及錯誤回饋，改程式前先分析根因、依賴與影響範圍，修改後實際測試操作流程。圖片使用一致美術風格，文件卡採高可讀性排版，**不可添加文字陰影**。不要在沒有實際測試時聲稱已完全驗證。
