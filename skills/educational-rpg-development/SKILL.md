# 教育互動 RPG 開發 Skill

## 啟動時必須先執行的保護程序

**任何新 RPG／解謎遊戲專案，在建立或改動程式碼前，都必須提醒使用者：**

> 這是一款新的遊戲。建議先在 GitHub 建立**全新的儲存庫（repository）**，不要沿用「校園真相調查局」或其他舊遊戲的儲存庫，否則可能覆蓋已完成的作品。你想為這款遊戲使用哪個新儲存庫？

1. 先確認**這是新遊戲，還是要維護舊遊戲**。新遊戲不得擅自使用舊 repo；若不明，問一個直接的澄清問題。
2. 新遊戲先建立獨立 repo，建議名稱與遊戲題材相符，例如 `school-mystery-rpg`。建立 GitHub 儲存庫通常需使用者同意或操作，沒有建立成功之前不得對舊儲存庫寫入。
3. 在任何 GitHub 寫入前先核對 `repository_full_name`、分支和目標檔案；與預期不符就停止。
4. **絕對不要**將新遊戲的 `index.html`、`assets/`、地圖或故事直接覆寫到 `daimg49-gif/education-rpg`。
5. 新遊戲先留一份可運作的初始版本，再進行後續開發；有條件時使用 feature branch 或 Pull Request。
6. 使用者若明確要求修改某一個**既有**遊戲，先確認對應 repo，再依現有專案進行修改，不必機械式要求新建 repo。

## 何時啟用

使用者要製作以下內容時：
- 適合國小學生的互動 RPG、解謎、偵探或角色扮演故事遊戲。
- 具有可走動地圖、角色互動、資料卡、蒐證和通關任務的教學遊戲。
- 校園新聞、媒體識讀、科學探究、鄉土文化或其他學習主題的沉浸式遊戲。
- 延續、改進或重用「校園真相調查局」的 UI、腳本、素材、證據審查邏輯。

## 工作流程

### 第一階段：設計先於程式

- 確認年級、人數、學習目標、關卡數、使用設備與預期時長。
- 先設計**每一案的事件引子、人物、可查證事實、場景、資料卡、答案與回饋**。
- 讓故事以具體事實呈現，不讓文件旁白替學生判斷。
- 先製作案件證據矩陣：必要證據、補充證據、可能引發錯誤推論／不適切引用資料。**這些分類只供內部判定，不在學生畫面上顯示**。
- 每案的標題與內文選項需確保唯一合理解，且不以措辭模糊來硬性限制學生。

### 第二階段：建立可玩的第一案

- 開場背景說明 → 第一案起始劇情 → 才開放地圖。
- 俯視地圖（可參照 Canvas 640×384、16×9 格、五場景配置）。
- 手機方向鍵／長按行走／調查鍵，與桌面方向鍵或 WASD。
- 人物對話、物件文件卡、蒐集資料、證據板。
- 在編輯區四步完成：**調查立場、標題、內文、引用證據**。
- 成功結案、錯誤回饋及返回修改都要可用。
- 第一案從開頭**實際玩到結案**，才擴充其他案件。

### 第三階段：批量擴充及美術

- 用共用資料結構定義場景與案件，不複製五套略有不同的審查函式。
- 地圖維持像素化俯視角；場景插圖用 WebP，文件卡採米色紙張與深色無陰影文字。
- 避免字面 `\n`、字體陰影、圖片上的預寫 UI、關閉鍵遮住內容、過長的一整段故事文字。
- 對學生保留探索空間；讓回饋指向推理方向，不能直接公布必要證據或答案。
- 完成五案後提供教學回顧與重新挑戰。

### 第四階段：測試、發布與回溯

- 所有修改先做**問題根因分析、影響範圍確認**，不要讓使用者判斷程式修法。
- 每次程式寫入前確認 HTML 起迄、script 標籤、語法及 DOM 元素存在。
- 特別確認 UI 的元素是**真實 DOM**，不是沒有方法的占位物件；本專案曾遇到 `letters.replaceChildren is not a function`。
- 驗證按鈕事件：每次點擊必有結果，正常／失敗／資料不足都能繼續操作。
- 實測手機瀏覽器；**語法通過不等於通關測試通過**。
- 新版部署後檢查網址、版本號、暫存，以及首頁、第一案、所有後續案件與重玩流程。
- 如未實際測試，要明確說明驗證限制，不能宣稱全部修好了。

## 本 Skill 的最高優先序提醒

**一個新遊戲 = 一個新的 GitHub repository。先提醒、先核對，再寫入。舊遊戲不得被覆蓋。**
